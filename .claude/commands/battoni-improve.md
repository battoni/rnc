# Improve (turn an AI mistake into a rule → PR)

> A developer hit a moment where the AI did something wrong. Capture it, **diagnose where the fix belongs**, draft the change, and open a PR so every rnc-derived project benefits — the rules system learns from real mistakes. Interactive; **opens a PR only after you approve the draft** (never pushes silently).
>
> **Usage:** `/battoni-improve [short description]`. Run from the rnc monorepo root.

---

## Step 1 — Gather the report

Use the description if one was passed; ask for whatever's missing (one tight round of questions):

1. **Which sub-project(s)?** `app.rnc` · `api.rnc` · `cortex` · root (one or more — rules are per-stack).
2. **What did the AI do wrong?** The concrete mistake — and the **file / area** if known.
3. **What should it have done?** The correct behavior.
4. **What should it NOT do?** The anti-pattern to ban.
5. *(optional)* A short code example, and: did a rule about this **already exist**?

## Step 2 — Classify the failure (this picks the fix)

Decide which of three it is — they fix differently:

- **🆕 Missing rule** — no rule covered this → **add** one.
- **✏️ Wrong / unclear rule** — a rule exists but was vague, wrong, or out of date → **sharpen** it (don't add a duplicate).
- **🔌 Rule existed but wasn't followed** — usually an **injection gap**, not a content gap: the rule/`RULES.md` was correct but never reached the agent (the pre-edit hook didn't inject it — wrong placement/folder, or a folder the hook doesn't cover). Fix the **delivery** (`cortex/hooks/inject-rules-context.py`, the file's folder placement), **not** the rule text. A repo without that hook (a tooling-only copy) injects nothing: there, delivery means moving the rule to where the agent already reads it — `CLAUDE.md`, a rule `/battoni-start-session` loads, or the skill for that sub-project. *(Easy to miss — otherwise you write a rule that already exists.)*

State the verdict explicitly; it's the first line of the PR.

## Step 3 — Diagnose the target (where the fix lives)

Search the existing rules for the closest home (**closest folder wins**), and name the target file:

| The fix is about… | Target |
| --- | --- |
| A broad app.rnc (Vue/TS) convention | `.claude/rules/celer-*` |
| A broad api.rnc (Laravel) convention | `.claude/rules/arcus-api-architecture.md` |
| A monorepo-wide convention | `.claude/rules/shared-conventions.md` |
| A specific unit / component / module | that folder's `RULES.md` (the versioned unit) |
| A project-wide always-true fact | `CLAUDE.md` |
| A command / flow that misbehaved | `.claude/commands/<cmd>.md` |
| A demand-loaded specialization | `.claude/skills/<skill>/SKILL.md` |
| Injection gap (Step 2 🔌) | `cortex/hooks/inject-rules-context.py` (or the file's folder placement); without that hook, the file the agent already reads |

Read the candidate file first — don't restate what it already says.

## Step 4 — Draft the change

Write the precise edit in the **house format**: a concrete **✅ do / ❌ don't** grounded in the report, citing the real file/pattern. Sharpen if a rule exists; add if missing; fix delivery if it's an injection gap. Never weaken a rule to fit a one-off — capture the **general principle** behind the mistake.

**`.cursor` is auto-mirrored — never hand-edit it.** Edit only the canonical `.claude/` source. The `.cursor/rules/*.mdc` twins are regenerated by `make sync-mirror` (`make sync-mirror-check` must stay green). This differs from projects that maintain the twin by hand: a repo whose Makefile has no `sync-mirror` (a tooling-only copy) edits the `.mdc` twin too, with a body identical to the `.claude` source.

**Versioned units:** if the target is a unit `RULES.md` (has a sibling `CHANGELOG.md`), bump the version + add a CHANGELOG entry per the `cortex-sync` skill. Global `.claude/rules/*` files carry no per-file version — just edit + mirror.

## Step 5 — Present & confirm (NO push yet)

Show: the **failure type**, the **target file**, and the **exact draft change** (diff). **Wait for the developer's approval.** This command makes no commit/push until they say go — approving the draft is not the same as authorizing a commit; get an explicit go.

## Step 6 — Open the PR (after approval only)

1. Branch: `improve/<slug>` off `main`.
2. Apply the edit. If a `.claude/rules` or `.claude/commands` file changed, run `make sync-mirror` (or, where there is no such target, apply the same edit to the `.mdc` twin) and stage the `.cursor` mirror alongside it.
3. Commit — conventional, **no `Co-Authored-By` / AI-signature trailer**: `docs(rules): <what improved>` (or `fix(cortex)` / `docs(cortex)` as fits the target).
4. Push; open a **draft** PR against `development` (if the remote has it, else `main`) with the template below, reviewer `battoni`.
5. Report the **PR URL**.

PR body template:
```markdown
## AI improvement
**Sub-projects:** <app.rnc/api.rnc/cortex/root>
**Failure type:** missing rule · wrong/unclear rule · rule not followed (injection gap)

**What the AI did wrong:** …
**What it should do:** …
**What it should NOT do:** …

**Fix:** `<file>` — <one line>
```

---

## Rules

- **Approval-gated:** open a PR **only** after the developer approves the draft (Step 5). This is the one outward action here — never silent.
- **One improvement = one focused PR.** Don't bundle unrelated feedback.
- **Route correctly:** a unit `RULES.md` fix goes to that unit's folder; global rules/commands/context are top-level `.claude/` or `CLAUDE.md`.
- **Don't over-fit:** ban the pattern, not the single instance; capture the principle.
- If it's an **injection gap**, fix delivery — adding rule text won't help if the agent never sees it.
