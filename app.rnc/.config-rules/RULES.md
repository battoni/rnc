# RULES — app.rnc Build & Config

> For AI agents. Governs app.rnc's root build/config files (they live at the project root
> where toolchains expect them; this folder holds their shared contract + changelog).

## Files governed

`vite.config.ts`, `eslint.config.ts`, `tsconfig.json` / `tsconfig.app.json` /
`tsconfig.node.json`, `.prettierrc.json`, `env.d.ts`, `components.d.ts`,
`.vscode/settings.json`.

## Intentional Decisions

- **`vite.config.ts` owns the module aliases** (`@AuthModule`, `@UserModule`, `@Helpers`,
  `@Composables`, etc.). Adding a module = add its alias here, in `tsconfig.app.json` `paths`
  AND in `vitest.config.ts` — **three files, not two.** This entry said two for as long as it
  has existed, and the third is the one that gets forgotten: `vitest.config.ts` is deliberately
  standalone so unit tests do not drag devtools and tailwind into jsdom, and that independence
  is exactly what lets it drift. Each file serves a different consumer, so a miss fails
  somewhere unrelated to the edit — the build is fine and the suite cannot resolve the import,
  or the suite is green and `type-check` denies the module exists.
- **`npm run check:aliases` asserts the three agree, and CI runs it.** See
  `scripts/check-aliases.mjs`, which also records why it is a script and not a Vitest spec
  (importing `vite.config.ts` under jsdom trips an esbuild invariant that names neither the
  file nor the import). It found five aliases declared only in `vitest.config.ts` on its first
  run, one of them pointing at a directory that does not exist. An alias resolving to a
  STYLESHEET is exempt and stays vite-only — `@ActiveTheme` is reached from one `@import`
  inside `colors.css`, which neither the suite (`css: false`) nor TypeScript ever resolves.
- **`vitest.config.ts` gives `VueI18nPlugin` the same include as vite: `./src/locales/*.json`.**
  Not `**` — that reaches `src/locales/local/` and precompiles the project overrides, which
  `src/libraries/i18n/index.ts` has to receive as plain strings to deep-merge over the core. A
  local message with a `{param}` then fails at translation time in every spec that mounts. It
  shipped that way and never fired only because rnc's local files are `{}`.
  `src/libraries/i18n/localOverrides.spec.ts` asserts the two globs agree and stop at the top level.
- **`unplugin-vue-components` auto-imports** everything under `src/components/*`,
  `src/modules/*`, `src/layouts/*`, plus PrimeVue via `PrimeVueResolver`. This is why Vue
  components are never imported in `<script setup>` — see `celer-02-vue-imports`.
  `components.d.ts` is GENERATED by this plugin — never hand-edit it.
- **`eslint.config.ts` is the enforcement engine** for most conventions (import order via
  `perfectionist`, `import type`, attribute order, `no-else-return`, empty-catch, locale
  JSON sorting, and **`$t()`-only-in-templates** via `vue/no-restricted-syntax`). Convention
  rules that are `[ESLint]`-tagged in `celer-01` live here.
- **Prettier + `prettier-plugin-tailwindcss`** owns Tailwind class ordering — never order
  classes by hand.
- **tsconfig is split**: `tsconfig.json` (solution/refs) → `tsconfig.app.json` (app code,
  holds `paths`) + `tsconfig.node.json` (vite/build tooling). Put app path aliases in
  `tsconfig.app.json`, not the root.

## Do Not

- Do not hand-edit `components.d.ts` (generated).
- Do not add an alias to vite without mirroring it in `tsconfig.app.json` paths AND
  `vitest.config.ts`. Run `npm run check:aliases` — it tells you which of the three is out of
  step, which is the thing the resulting error message never does.
- Do not widen the `VueI18nPlugin` include past `./src/locales/*.json` in either config.
- Do not relax ESLint rules to silence a convention violation — fix the code.
